# 설계 근거

## 1. 왜 컴패니언 컴퓨터와 PX4를 분리하는가

PX4는 센서 융합, 자세제어, 위치제어, VTOL 천이, 모터 출력처럼 실시간성과 안정성이 중요한 기능을 담당한다.

컴패니언 컴퓨터는 다음과 같이 계산량이 크거나 임무 의존적인 기능을 담당한다.

- 임무계획과 재계획
- 표적 탐지·추적·위치추정
- 임무 상태 판단
- MissionRaw·Offboard·RTL 선택
- 로그와 검증 보고서 생성

이 분리를 통해 상위 임무 소프트웨어를 독립적으로 시험하면서도, 비행 안정화는 검증된 PX4 계층에 맡길 수 있다.

## 2. 왜 MissionRaw를 사용하는가

MissionRaw 항목은 MAVLink `MISSION_ITEM_INT` 필드와 동일한 구조를 사용한다. 따라서 일반 웨이포인트뿐 아니라 MAVLink 명령과 세부 필드를 명시적으로 다룰 수 있다.

프로젝트에서는 MissionRaw를 다음 용도로 사용한다.

- 장거리 웨이포인트 비행
- PX4 임무 저장소 업로드
- 임무 진행률 수신
- 저장 임무 재다운로드
- 원본과 항목별 무결성 대조

## 3. 왜 MissionRaw와 Offboard를 혼합하는가

MissionRaw만 사용하면 링크가 일시적으로 끊겨도 PX4가 사전 임무를 계속 수행할 수 있다. 반면 비전 기반 표적 접근처럼 비행 중 계속 갱신되는 제어에는 적합하지 않다.

Offboard는 컴패니언 컴퓨터가 위치·속도·자세 Setpoint를 전달할 수 있어 정밀 접근에 적합하지만, 지속적인 Setpoint와 연결 상태가 필요하다.

따라서 역할을 다음처럼 나눈다.

```text
장거리 경로      = MissionRaw
이륙·착륙·천이   = MAVSDK Action
표적 접근·정렬   = Offboard
상위 시스템 실패 = PX4 RTL
```

## 4. 왜 업로드 후 재다운로드 검증을 수행하는가

성공 응답만으로 저장 내용이 의도와 동일하다고 가정하지 않는다.

검증 절차:

1. 컴패니언 컴퓨터에서 MissionPlan 생성
2. MissionRaw 항목 변환
3. PX4 임무 저장소에 업로드
4. 저장된 임무 재다운로드
5. 원본과 seq, 명령, 좌표, 고도, 도달 반경 등 비교
6. 불일치가 없을 때만 다음 단계 허용

이는 실제 명령 실행 전 데이터 무결성을 검증하는 안전 경계다.

## 5. 왜 칼만필터를 사용하는가

영상 탐지 좌표에는 픽셀 오차, 카메라 흔들림, 자세 변화, 탐지 누락과 이상치가 포함될 수 있다. 원시 탐지값을 곧바로 Offboard 명령으로 변환하면 기체 명령이 흔들릴 수 있다.

칼만필터 계층은 다음을 제공한다.

- 위치 노이즈 완화
- 표적 속도 추정
- 짧은 탐지 누락 중 예측
- 큰 이상치 제거
- 공분산 기반 추적 안정성 판단

Offboard 전환은 필터가 초기화됐다는 이유만으로 허용하지 않고, 신뢰도·공분산·데이터 수명 조건을 모두 통과해야 한다.

## 6. 왜 실제 비행보다 자동시험을 먼저 확장하는가

VTOL 시험은 비용과 위험이 크다. 상태머신과 고장 대응을 비행 중 처음 확인해서는 안 된다.

이 프로젝트는 다음 순서를 따른다.

```text
순수 함수·자료구조 시험
→ Fake MAVSDK 시험
→ Virtual FC 통합시험
→ Arm 없는 실제 FC 통신
→ 프로펠러 제거 명령시험
→ 지상 통합시험
→ 계류·저위험 시험
→ 제한된 실제 비행
```
